## Cycle de vie du handler PLAYER_TARGET_CHANGED dans AutoLog.lua

### 1. Création : handler éteint
À la ligne 74, `targetEv = W.On("PLAYER_TARGET_CHANGED", fn, nil, true)` crée le handler avec `always = nil` et `inactive = true`.

- Dans `W.On` (Core.lua), `active = not inactive`, donc `h.active = false` dès la création.
- `W.On` appelle ensuite `Sync("PLAYER_TARGET_CHANGED")`. Ce handler est le seul de cet événement, et il est inactif. `want` reste donc `false`, ce qui est égal à `registered[event] or false`, et `Sync` retourne sans rien faire.
- L'événement n'est donc **pas enregistré** auprès du jeu (`RegisterEvent` n'est jamais appelé). Tant que rien ne l'allume, le changement de cible ne coûte rien.
- `targetEv` est déclaré `local` en ligne 33, avant `WatchTargets`. La fonction le capture comme upvalue, ce qui est nécessaire parce que l'assignation n'a lieu qu'en ligne 74.

### 2. Pilotage : WatchTargets
`WatchTargets()` appelle `W.Activate(targetEv, condition)`, avec :
`db and db.raids and kind == "none" and not worldBoss`

où `kind` est le second retour de `IsInInstance()`. Le handler est **allumé** seulement si toutes ces conditions sont vraies :
1. `db` est chargé (donc après `W.OnReady`).
2. L'option « Raids (and world bosses) » est cochée (`db.raids`).
3. Le joueur est en monde ouvert (`kind == "none"`, pas en instance).
4. Aucun world boss n'est déjà en cours de suivi (`not worldBoss`).

Dans tous les autres cas, il est **éteint**. L'expression peut valoir `nil` si `db` est nil, mais `W.Activate` la normalise avec `on and true or false`.

`WatchTargets` est appelé uniquement depuis `CheckAutoLog` (ligne 42), après les gardes `db` et `W.Overlap("autoLog")`. Il est donc réévalué à chaque passage dans `CheckAutoLog`. Les déclencheurs sont :
- `PLAYER_ENTERING_WORLD`, `ZONE_CHANGED_NEW_AREA`, `PLAYER_DIFFICULTY_CHANGED` et `UPDATE_INSTANCE_INFO`, via `Later()` avec un délai de 2 s.
- Le changement de la case « Raids » ou « Dungeons » dans l'interface, via `CheckAutoLog()`.
- Les fins de combat de world boss (`WorldBossOver`).
- Les nouvelles tentatives après limitation de débit (`W.After(3, CheckAutoLog)`).
- `/wl logdebug`, quand le mode debug passe à ON.

Un cas particulier : si `W.Overlap("autoLog")` est vrai (EllesmereUI journalise déjà), `CheckAutoLog` sort avant `WatchTargets`. Le handler garde alors son dernier état, mais il est déjà éteint tant qu'on n'est pas passé par un allumage.

Cycle typique :
- Le joueur entre en monde ouvert avec l'option raids : le handler est allumé.
- Il cible un world boss : le handler met `worldBoss = true` et appelle `Later()`. `CheckAutoLog` réévalue `WatchTargets`, et `not worldBoss` est faux, donc le handler est **éteint**. On ne regarde plus les cibles pendant le combat de boss.
- Quand le combat se termine, `WorldBossOver` remet `worldBoss = false` et appelle `CheckAutoLog`, ce qui rallume le handler si on est toujours en monde ouvert.
- Entrer en instance (`kind` différent de `"none"`) ou décocher l'option raids l'éteint aussi.
- `ZONE_CHANGED_NEW_AREA` remet `worldBoss = false`, puis `Later()` réévalue la condition.

### 3. Effet sur l'enregistrement de l'événement (Core.lua, `Sync`)
`W.Activate` modifie `h.active`, puis appelle `Sync(h.event)`. `Sync` recalcule `want` : y a-t-il au moins un handler actif dont le fichier n'est pas désactivé (`offFiles`) ? Il le compare à `registered[event]`.

- Allumer le handler : `want = true` et `registered` valait `false`. `registered[event]` passe à `true`, puis `pcall(evFrame.RegisterEvent, evFrame, event)` enregistre l'événement sur la frame unique. Le `pcall` protège contre les événements qui n'existent pas sur tous les clients.
- Éteindre le handler : `want = false` et `registered` valait `true`. `registered[event]` passe à `false`, puis `evFrame:UnregisterEvent(event)` désenregistre l'événement. Le jeu cesse alors d'envoyer `PLAYER_TARGET_CHANGED` à l'addon.
- Si l'état ne change pas (`want == registered`), `Sync` retourne immédiatement. `W.Activate` sort aussi plus tôt si `h.active == on`. Les appels répétés sont donc idempotents et peu coûteux.

Il y a une seconde barrière dans `Run` : un handler inactif n'est de toute façon pas exécuté (`h.active` testé). Il faut aussi que `W.access == true` (joueur autorisé, guilde) puisque `always` est nil. Le handler ne tourne donc que si l'utilisateur est autorisé. De plus, si le module est coupé dans Settings > Modules (`offFiles["AutoLog.lua"]`), le handler ne tourne pas et `Sync` désenregistre l'événement.

Les handlers AutoLog étant tous sans `always`, aucun ne s'exécute pour un joueur non autorisé. Pour le gating d'accès, rien n'est contourné ici.

### 4. Pourquoi ce design
- **Performance** : `PLAYER_TARGET_CHANGED` est un événement très fréquent (chaque changement de cible). L'enregistrer en permanence ferait appeler le dispatcher (`Run`, `W.Measure`, `pcall`) pour rien. Le commentaire de Core le dit : « a frequent event costs nothing while no option or window needs it ».
- **Utilité ciblée** : détecter un world boss n'a de sens qu'en monde ouvert, avec l'option raids active, et tant qu'aucun boss n'est déjà suivi. En instance, le type d'instance suffit à décider. Une fois le boss détecté, la fin du suivi dépend du combat (`PLAYER_REGEN_*`) et du délai de 5 minutes, pas des changements de cible.
- **Mécanisme central** : au lieu d'enregistrer et de désenregistrer à la main, le module déclare son handler une fois, éteint, et laisse `Sync` gérer l'enregistrement de manière déclarative et cohérente avec les modules désactivés.
- **Source unique de vérité** : `WatchTargets` est appelé à tous les endroits où l'état pertinent peut changer (zone, option, fin de combat), donc la condition est toujours recalculée au même endroit.

### Remarques de rigueur
- Le handler est créé éteint, donc `PLAYER_TARGET_CHANGED` n'est pas enregistré tant que `WatchTargets` ne l'a pas allumé. Il n'est pas enregistré au chargement du fichier.
- Il n'y a pas d'API inventée ici : `RegisterEvent` et `UnregisterEvent` sont des méthodes de frame standard, et leur appel est centralisé dans Core.
- Un petit détail à surveiller : `WatchTargets` utilise `db and ...`, mais `targetEv` pourrait théoriquement être nil si `CheckAutoLog` était appelé avant la ligne 74. Ce n'est pas le cas en pratique, car les appels viennent d'événements ou de `W.After`, après le chargement du fichier. `W.Activate` gère de toute façon `not h` (retour immédiat).
